READING IT.

EXACTLY 1 ROW DIFFERS, and it is a GAIN, not a restoration:
the room's REGION now opens the ROOM menu where it opened the floor
popup.  The room menu was ONLY EVER REACHABLE FROM THE LABEL -- before
A1b the region was not in shape(), so itemAt returned None there.  Nobody
should later 'restore' the label-only behaviour: it was a limitation, not
a design.

OpeningItem IS THE ROW TO READ SECOND, and it is UNCHANGED.  Ranking a
door above its wall in the resolver was the deviation most likely to
alter behaviour nobody asked about -- and it does not, because a door
ALREADY won by z (OPENING_Z 6.0 > WALL_Z 5.0).  The ranking preserves the
existing answer rather than introducing one.

StairItem IS MEASURED, NOT REASONED.  It subclasses FurnishingItem, the
resolver returns the instance, and Python's MRO reaches
StairItem.contextMenuEvent.  That was the prediction; this is the
measurement, and they agree.

THE raise_to_front ROWS ARE THE ONES THAT WOULD HAVE BITTEN.  Right-
clicking a wall, a door or a furnishing INSIDE a room whose label has
been dragged -- so the room sits at z 10 above their 5, 6 and 3 -- still
reaches each item's own menu, because `RoomItem.contextMenuEvent` asks
the same `_outranked_at` helper that `mousePressEvent` does.  A test on a
freshly loaded plan would pass while the real gesture failed.

NO TYPE WAS UNTESTABLE.  ReferenceImageItem was expected to need a file;
a QImage needs none, so it is measured too -- which matters because it is
the one type ranked BELOW the room, and the row confirms a right-click on
the backdrop still reaches it.  Nothing was skipped quietly.
