-- READING IT ---------------------------------------------------------------

A MOVE THAT RETURNS THE ROOM WHENCE IT CAME IS BALANCED. move #1 out is
+4 walls / +5 vertices; move #2 back is -4 / -5, exactly to baseline. That is
why "move a room and move it back" shows nothing, and why the accumulation is
invisible to any test that does it.

A MOVE THAT LANDS THE ROOM SOMEWHERE NEW COSTS +2 WALLS AND +2 VERTICES, EVERY
TIME, PERMANENTLY -- and both new vertices are DEGREE-2 COLLINEAR. The collinear
count runs 0, 0, 2, 4, 6, 8, 10 across six walks. It is linear, monotonic, and
it never comes back down.

SHUFFLE IS NOT THE PRODUCER. A shuffled room stays floating (P4.3: "leaving
shuffle joins nothing automatically"), so join never runs -- the first shuffled
move pays the extract cost once and every later one is +0/+0. Repeated
shuffling does not accumulate.

-- THE CALL SITE ------------------------------------------------------------

Per walk gesture, measured:

    walls.split_wall_at   from extract.py:232, inside join_room
    Vertex.at         x4  from walls.py:1184  WallItem.__init__
    Vertex.at         x4  from walls.py:1185  WallItem.__init__
    Vertex.at         x4  from extract.py:178 _private
    walls.merge_wall  x6  from extract.py:254, inside join_room

Twelve corners are minted per gesture and ten are reabsorbed. THE TWO THAT
REMAIN ARE THE SPLITS: join_room splits every plan wall a landing room corner
rests on (extract.py:232), which is correct -- that is how the corner becomes a
real junction. The vertex is created BY DESIGN.

WAS IT EVER INTENDED TO BE REMOVED AGAIN? NO -- and that is the finding.
join_room's own docstring says coalescing "touches only the runs the room's own
walls sit in (merge_wall is per-run and refuses through degree-3 vertices),
never the whole plan". merge_wall runs six times per gesture and does reabsorb
the room's own privatised walls. But when the room LEAVES that spot on a later
gesture, the split it caused is in a run the room no longer occupies, so
nothing revisits it. THE SPLIT IS PLACED BY A JOIN AND OWNED BY NOBODY
AFTERWARDS.

So this is not a bug in split_wall_at, and not a leak in extract/join taken as
a pair. It is an ASYMMETRY: the join splits, and no gesture un-splits.

-- ONE INSTRUMENT ERROR, RECORDED BECAUSE IT ALMOST SHIPPED ------------------

The first run reported degree-2 = 0 on a 103-wall plan. Cause: `WallItem.v1`
returns the vertex's UID STRING, not the object; `_v1` holds the Vertex. An
isinstance filter then silently dropped every wall corner. 206 ends over 97
objects should average 2.1, and a zero was not credible -- which is what caught
it.

The second run reported no split at all. Cause: `extract.py:29` does
`from floorplanner.walls import split_wall_at`, so wrapping
`walls.split_wall_at` left extract's own name bound to the original. THE
WRAPPER WAS BOUND TO THE WRONG REFERENCE. Both are the "grep for identifiers,
parse for shapes" family, arriving in an instrument rather than in a census.
